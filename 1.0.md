# Protocol 1.0 (ngspades)

Protocol 1.0 is the protocol of the **Shoot and Destroy** server. It starts
from the wire format of OpenSpades' abandoned `ngspades` branch
("WorldOfSpades 0.1"), with that reference's defects fixed and the packets a
whole game needs added (chat, building, damage, game modes). It is not
compatible with "WorldOfSpades 0.1": the protocol name differs, so the two
can never be confused.

**Current protocol revision: 1.3** (three weapon slots, the compact player
trajectory, the jetpack bits). The revision is informational: the server
negotiates nothing on it. There is no backward compatibility inside 1.0 yet —
a wire change updates the server and the client together.

This document is the implementer's reference: every packet, what it is for,
what the server sends, what it expects, and what a client must send. Where a
byte layout matters it is given exactly, with a hex example. A complete
dependency-free C codec is in [`examples/c/`](examples/c/); a GDScript one is
in [`examples/godot/`](examples/godot/).

Companion documents: [`0.75.md`](0.75.md) for the coordinate system and the
classic protocol, [`master.md`](master.md) for the server list, WebRTC
signalling and connect tokens.

---

## 1. What 1.0 changes against 0.75

| Topic | 0.75 | 1.0 |
| --- | --- | --- |
| Integers | fixed width | LEB128 varints, zigzag for signed |
| Strings | NUL-terminated or fixed size | length-prefixed bytes (≤ 1 MiB), UTF-8 |
| Handshake | ENet connect data only | connect magic + Greeting / InitiateConnection / certificates, protocol name, locale, nonces |
| Map | zlib VXL | `vxl` (same bytes) or `ngmap` (better compression), client picks |
| World | one packet per subject | generic **entities**, delta-encoded |
| Movement | position samples | **trajectories** the client extrapolates |
| Player vs body | one thing, 8-bit id | player record (name, score, flags) separate from its entity |
| Input | 8 booleans | analogue `xmove`/`ymove` (-127..127), stance, buttons, sprint, chat, jetpack |
| Weapons | 3 hardcoded | `WeaponParameters` sent by the server, 3 slots + melee + block |
| Damage | `KillAction` with a kill type | `HitEntity`/`HitTerrain` with fire and hit positions, `Damage` with a type |
| Extensibility | none | unknown ids and unknown map keys are ignored; `GenericCommand` |

## 2. Transport

### 2.1 ENet (desktop, consoles)

| Setting | Value |
| --- | --- |
| Transport | ENet 1.3 over UDP, IPv4 and IPv6 |
| Port | 32887 by convention, the same as 0.75 |
| Connect data | `0x08101919` (135272729) |
| Channels | 2. Channel 0: reliable, ordered — everything. Channel 1: unreliable, sequenced — movement only |
| Compression | ENet's range coder |
| Framing | one ENet packet = `u8 id` + payload |

The reference sent everything on one channel. Our server sends everything on
channel 0 and reads both; a client should send its own body updates
(`ClientSideEntityUpdate`, and an `EntityUpdate` carrying only a trajectory)
on channel 1 unreliable, and everything else reliable on channel 0.

An update that must be seen **before** an action goes reliable on channel 0:
right before a `HitEntity` or a block build/dig, send one
`ClientSideEntityUpdate` reliably, or the server does not yet know you are
firing or holding the right tool and refuses the action.

```c
ENetHost *host = enet_host_create(NULL, 1, 2, 0, 0);
enet_host_compress_with_range_coder(host);
ENetPeer *peer = enet_host_connect(host, &address, 2, 0x08101919);
```

### 2.2 WebRTC (browsers)

A browser cannot send UDP. It reaches our servers over WebRTC DataChannels;
the packets are identical, only the carrier changes. Signalling goes through
our master ([`master.md`](master.md) section 5).

* Two DataChannels, created **before** the offer:
  `reliable` (defaults: reliable, ordered) = ENet channel 0;
  `unreliable` ({ ordered: false, maxRetransmits: 0 }) = ENet channel 1.
  Any other label is closed by the server.
* A **text** message is control: after both channels are open, send
  `connect 135272729` on `reliable` (the connect data in decimal). The
  server refuses anything else with ENet's refusal (`3` = wrong protocol).
* A **binary** message is exactly one 1.0 packet, at most **16 KB**.
* The server ends the connection with the text `disconnect <reason>`, then
  closes the peer. A binary message before `connect` is dropped.
* The server sends everything on `reliable`; it reads both.

### 2.3 Disconnect reasons

Sent as the ENet disconnect data (or as `disconnect <n>` over WebRTC):

| Value | Meaning |
| --- | --- |
| 0 | unknown |
| 1 | internal server error |
| 2 | server full |
| 3 | kicked: a `Kick` packet with the text came first |
| 4 | server stopped |
| 5 | handshake timeout |
| 6 | malformed packet |
| 7 | protocol mismatch |

**Careful:** vanilla uses the same field with another table (1 = banned,
2 = connection limit, 3 = wrong protocol). The meaning depends on the
protocol the connection was opened with. The ambiguous case: connecting with
the 1.0 magic to a vanilla server gives `3` with no `Kick`; treat that as
"not a 1.0 server" and reconnect with `3`.

### 2.4 Handshake timeouts

The server drops a connection that does not advance: 10 s to send
`InitiateConnection`, 10 s (ours; 60 s in the reference) for the
certificate, 300 s for the map transfer. There is no timeout in the game;
ENet's peer timeout applies.

### 2.5 Connection state machine

```
client                                            server
  ENet connect (0x08101919) or WebRTC "connect" -->
             <-------------------------------- Greeting (1)            10 s
  InitiateConnection (2) ------------------------>
             <------------------------ ServerCertificate (3)
  ClientCertificate (4) ------------------------->
             <------------------------ GameStateHeader (6)           300 s
             <------------------------ MapData (7) x N
             <------------------------ MapDataFinal (11)
  MapDataAcknowledge (10) ----------------------->   (after decoding)
             <------------------------ GameStateFinal (8)
  GenericCommand "join <team> <weapon>" --------->
             <------------------------ GenericCommand "local-player <id>"
             <------------------------ EntityUpdate / PlayerUpdate / TerrainUpdate ...
```

When the world changes (a new round, `/reset`), the server restarts the
transfer at `GameStateHeader` for every connection. The player is removed and
the client has to `join` again. Packets still in flight are dropped, not a
protocol error.

## 3. Encoding

Every multi-byte fixed-width value is **little-endian**.

| Name | Encoding |
| --- | --- |
| `u8`, `u16`, `u32` | fixed width, little-endian |
| `f32` | IEEE-754 single, bit pattern written as `u32` |
| `vec3` | `f32 x, f32 y, f32 z` (12 bytes) |
| `varint` | unsigned LEB128: 7 bits per byte, low group first, bit 7 = more follows |
| `svarint` | zigzag then varint: `n >= 0 → 2n`, `n < 0 → 2(-1-n)+1` |
| `bytes` | `varint length` + raw bytes; length ≤ 1 MiB |
| `string` | `bytes` of UTF-8, no NUL inside |
| `color` | 3 bytes, **B, G, R** |
| `blockcoord` | `svarint x, svarint y, svarint z` |
| `rotation` | `vec3`: quaternion `x,y,z` with `w ≥ 0`; `w = sqrt(1 - x² - y² - z²)` |
| `map` | repeated `string key, string value`, terminated by an empty key |

Varint examples: `0 → 00`, `127 → 7F`, `128 → 80 01`, `300 → AC 02`.
Zigzag examples: `0 → 00`, `-1 → 01`, `1 → 02`, `-2 → 03`.

### 3.1 Decoder rules (part of the protocol)

A decoder must reject, not paper over:

* a truncated packet;
* a varint longer than 10 bytes;
* a string longer than 1 MiB, or with a NUL in it;
* a string that is not valid UTF-8 (names, chat);
* a mask bit it does not know (its payload cannot be measured);
* an enum value out of range that a table would index.

**Mask bits are not self-describing.** A decoder that does not know a mask
bit cannot tell how many bytes belong to it and the rest of the packet is
misread. That is why unknown *packet ids* and unknown *map keys* can be
skipped freely, but new mask bits and new trailing fields require both sides
to change together.

### 3.2 Reference codec

The complete primitive codec is [`examples/c/proto10.c`](examples/c/proto10.c)
(`p10_reader`, `p10_writer`, `p10_read_varint`, `p10_write_string`, ...).
Use it or port it. It follows the rule above: one sticky `error` flag, checked
once after decoding the whole packet, plus `p10_at_end` for packets whose
length is implied by the end of the packet.

## 4. Session packets

### 1 `Greeting` (S→C)

```
string  magic    "Hello" (the client rejects anything else)
bytes   nonce    128 random bytes
```

Hex: `01 05 48 65 6C 6C 6F 80 01 <128 bytes>`.

The nonce is used by the connect token (section 5.4). A client that receives
**any other packet id before the Greeting** must treat the server as not 1.0:
about 1 in 50 public 0.75 servers accept the magic and then speak 0.75.

### 2 `InitiateConnection` (C→S)

```
string  protocolName    exactly "WorldOfSpades 1.0"
u16     majorVersion    1
u16     minorVersion    3          (the protocol revision, informational)
u16     revision        0
string  packageString   your build, free text, <= 256 bytes
string  environment    OS/CPU, <= 1024 bytes
string  locale          e.g. "pt_BR", <= 256 bytes
string  playerName      UTF-8, <= 63 bytes
bytes   nonce           256 random bytes
u8      mapQuality      0 = send VXL; 1..100 = ngmap at that quality
```

Any other `protocolName` gets `ProtocolMismatch` (7).

`mapQuality` 0 means "I cannot decode ngmap, send `map-format=vxl`"; 1..100
means "ngmap is fine", clamped by the server to 20..100. The server may still
answer VXL (encoding failed, map too large): **trust `GameStateHeader`'s
`map-format`, not what you asked for.** A client without the ngmap codec
sends 0 and only needs the VXL loader.

```c
/* the codec's shape; see examples/c/proto10.c */
p10_write_string(&w, "WorldOfSpades 1.0");
p10_write_u16(&w, 1); p10_write_u16(&w, 3); p10_write_u16(&w, 0);
p10_write_string(&w, "MyGame 1.0");
p10_write_string(&w, "Linux x86_64");
p10_write_string(&w, "en_US");
p10_write_string(&w, "Player");
p10_write_bytes(&w, nonce, 256);
p10_write_u8(&w, 0);   /* 0 = VXL, 80 = ngmap q80 */
```

### 3 `ServerCertificate` / 4 `ClientCertificate`

```
u8     isValid      0 = no certificate, nothing follows
bytes  certificate  only if isValid != 0
bytes  signature    only if isValid != 0
```

Both sides send `isValid = 0` normally; nothing is validated. The packets
exist so accounts can be added without changing the handshake. Our server
uses the client certificate to carry a **connect token** (section 5.4).

### 5 `Kick` (S→C)

```
string  reason   shown to the player
```

Sent before the disconnect with reason 3 (`Misc`). Many servers use
`enet_peer_disconnect_later` so the text gets out. Show the text.

## 5. Game state transfer

### 5.1 `GameStateHeader` (6, S→C)

```
map  properties
```

| Key | Example | Meaning |
| --- | --- | --- |
| `map-name` | `Pinpoint` | |
| `map-format` | `ngmap` or `vxl` | how to decode the `MapData` stream |
| `map-size` | `512,512,64` | width, height, depth |
| `map-bytes` | `1834211` | total stream size, for a progress bar (optional) |
| `map-crc32` | `3f2a91c7` | CRC32 (zlib's) of the exact `MapData` stream, 8 hex digits (optional) |

The server clamps ngmap quality to 20..100 and falls back to `vxl`; the key
is authoritative.

**Map cache.** A client that already holds the stream answers the header with
the `GenericCommand` `map-cached 1`; the server then sends no `MapData` at
all and goes straight to `MapDataFinal`. Answer `map-cached 0` when you do
not have it. The server waits 3 seconds for the answer, so a client that
never sends it only loses 3 s. The key is the **stream**, not the map: the
CRC32 and byte count of the bytes the server would send, so two qualities of
one map, or one map after an edit, are different cache entries.

### 5.2 `MapData` (7, S→C) and `MapDataFinal` (11) / `MapDataAcknowledge` (10)

```
bytes  fragment     one piece of the stream, in order
```

Append every fragment; the concatenation is one stream. `MapDataFinal` (no
payload) ends it. Decode the whole map, **apply the `TerrainUpdate`s that
arrived during the transfer in order**, then send `MapDataAcknowledge` (no
payload). Only after the acknowledge does the server send `GameStateFinal`.
The server keeps broadcasting terrain edits to loading connections, so keep
them until the map is ready.

A failed or missing `MapDataAcknowledge` stalls the join; it is the one
packet implementations forget.

### 5.3 Map formats

**`vxl`** — the zlib-compressed VXL, exactly the bytes 0.75 sends in
`MapChunk`. One loader serves both protocols.

**`ngmap`** — zlib stream (2-byte header, Adler-32 trailer). Decompressed:

```
u32  signature = 0x1145148A
u16  width
u16  height
u16  depth            (<= 64)
u8   quality          (1..100)
     geometry         one entry per column, boustrophedon:
                      y 0..h-1; x 0..w-1 on even y, w-1..0 on odd y
u32  jpegLength
u8[jpegLength]        JPEG holding the lossy colour tiles
     colour blocks    to the end of the stream
```

A column entry is a format byte then either a run-length list of `u8` toggle
positions (first byte carries `0x80` when the column starts solid at z 0,
last byte is always `depth`) or a bitmap of 16-voxel slices. Colours are cut
into 8x8x8 cells with one of six formats (constant, linear, planar,
volumetric; raw or interpolated, some in JPEG tiles).

**Do not re-implement ngmap from this summary.** Port
`GameMap_ngmap.cpp` from the ngspades reference (about 1,900 lines) or ship
the C++ codec behind a C interface. It needs zlib and a JPEG decoder. Use
`mapQuality = 0` and skip it entirely if your client only needs to work.

### 5.4 The connect token (optional, ours)

Our server admits a UDP player from a non-local address only with a token
from our master, so a join flood is rate-limited at the master. After the
Greeting, post `{"address": "ip:port", "nonce": "<base64>"}` (the address you
connected to, the Greeting's 128-byte nonce) to the master's
`POST /v1/token`; send the answer as your `ClientCertificate` with
`isValid = 1`:

| Part | Bytes |
| --- | --- |
| certificate | `"SADT"`, version `u8` 1, the server's Ed25519 public key (32), expiry `u64` LE (Unix seconds, 60 s on), nonce length `u8`, the nonce |
| signature | Ed25519 by the master over the certificate (64) |

Not needed: a local address, a WebRTC connection (its offer went through the
master), a server that has not heard the master's key recently,
`[master] connect_tokens = false`. A client that gets no token within 5 s
sends an empty certificate and tries anyway.

### 5.5 `GameStateFinal` (8, S→C)

```
map      properties       world parameters (below)
varint   entityCount
         entityCount x entity update item (section 6.4), each with Create
varint   playerCount
         playerCount x player update item (section 6.10), each with Create
```

After this packet the connection is in the game. Take the world parameters,
then build the world: every body and every player already in the match.

**World parameters** (all values are strings, parsed as numbers):

| Key | Default | Meaning |
| --- | --- | --- |
| `player-jump-vel` | `0.36` | upward velocity added on jump |
| `fall-damage-vel` | `0.58` | landing speed where fall damage starts |
| `fall-damage-fatal-vel` | `1` | landing speed that kills |
| `fog-distance` | `96` | where bodies and effects stop (32..256) |
| `fog-color` | `0.6,0.7,0.9` | r,g,b 0..1 |
| `gamemode` | | the mode's wire name (`ctf`, `ngctf`, `tc`, `arena`, `zombie`, `koth`, ...) |
| `team1-name`, `team2-name` | | team names |
| `team1-color`, `team2-color` | | r,g,b 0..255 |
| `capture-limit` | | CTF captures to win |
| `aim-assist` | `0` | 1 = the server allows aim assist |
| `jetpack-fuel`, `jetpack-regen`, `jetpack-thrust`, `jetpack-max-rise`, `jetpack-air-control`, `jetpack-glide-control`, `jetpack-ignition`, `jetpack-refill-delay`, `jetpack-ceiling` | | jetpack figures, only when the server has the jetpack |
| `sentry-lifetime` | | seconds a sentry lives |

Ignore unknown keys. (The reference threw and disconnected on one; 1.0 does
not.)

## 6. Entities and players

### 6.1 The model

* A **player** is a participant: id, name, team, score, flags. It exists
  whether or not it has a body.
* An **entity** is anything simulated: a body, a grenade, a rocket, a flag, a
  command post, a sentry, a crate.
* A player's body has **the same id as the player**. Players use ids
  0..255; everything else uses **256 and up**. Fixed objective ids are
  `0x7FFF0000` and up (section 8).
* Ownership is not on the wire: it follows from the id rule. Bots are player
  records whose entity nobody owns.

### 6.2 Coordinates

Exactly as 0.75: `x`, `y` horizontal, **`z` grows downwards**, gravity
`(0, 0, +32)` blocks/s², a jump subtracts `player-jump-vel` from
`velocity.z`. Positions in blocks, velocities in blocks per second. If your
engine is Y-up, convert at the boundary: `(x, 63 - z, y)`; the look direction
is `(-cos(pitch)·sin(yaw), cos(pitch)·cos(yaw), sin(pitch))` with `pitch`
positive looking down.

### 6.3 Enumerations

```c
enum entity_type { PLAYER, GRENADE, ROCKET, COMMAND_POST, FLAG, CHECKPOINT,
                   VEHICLE = 6,
                   /* ours, after the reference's seven */
                   SENTRY = 7, LANDMINE = 8, DYNAMITE = 9, DRILL = 10,
                   AMMO_CRATE = 11, HEALTH_CRATE = 12 };
enum event_type  { JUMP, RELOAD_WEAPON, SUICIDE, EXPLODE, FIRE, USE_PERK };
enum tool_slot   { MELEE, BLOCK, WEAPON1, WEAPON2, WEAPON3 };
enum stance      { STAND, CROUCH, PRONE };
enum hit_type    { UNSPECIFIED, TORSO, HEAD, LIMB };
enum damage_type { UNKNOWN, SUICIDE, FALL, POISON, MELEE, DIG, BLOCK,
                   WEAPON1, WEAPON2, WEAPON3, GRENADE,
                   VEHICLE_EXPLOSION, VEHICLE, SENTRY };
```

| 0.75 | 1.0 |
| --- | --- |
| spade | `MELEE` (digging is `HitTerrain` with `DIG`) |
| block | `BLOCK` |
| gun | `WEAPON1` (the class's primary gun) |
| second gun | `WEAPON2` (the class's revolver; zero parameters when it has none) |
| grenade / drill | `WEAPON3` |

`Weapon1`/`Weapon2` in a `Damage`, `EntityDie` or `HitEntity` mean **the gun
in hand**, not a hardcoded gun: the server refuses a hit from a slot the
player is not holding.

### 6.4 Entity update item

Used by `EntityUpdate`, `ClientSideEntityUpdate` and `GameStateFinal`:

```
varint  entityId
u8      mask                 bits below, in this order:
  bit 0 Create        -> u8 entityType
                        if Player:
                            bytes bodySkin
                            bytes weaponSkin[3]
                            weaponParams[3]
                        if the type carries an owner
                        (COMMAND_POST, FLAG, CHECKPOINT, SENTRY, LANDMINE,
                         DYNAMITE, DRILL, AMMO/HEALTH_CRATE):
                            varint owner     (P10_NO_OWNER = 0xFFFFFFFF)
                            u8     team      (0, 1, 255)
  bit 1 Flags         -> u8 entityFlags
  bit 2 Trajectory    -> trajectory (6.5)
  bit 3 PlayerInput   -> u8 inputFlags, i8 xmove, i8 ymove
  bit 4 Tool          -> u8 toolSlot
  bit 5 BlockColor    -> color (B,G,R)
  bit 6 Health        -> u8 health
```

**The fields follow the order above, not the bit order.** Write Create, then
Flags, then Trajectory, then Input, Tool, BlockColor, Health.

Entity flags: bit 0 `playerClip`, bit 1 `weaponClip`, bit 2 `fly`, bit 3
`jetpack` (this body wears a jetpack). Bits 4..7 are invalid.

Input flags: bit 0 primary, bit 1 secondary, bit 2 chat (typing), bit 3
sprint, bit 4 jetpack thrust, bits 6..7 stance. Bit 5 is unused and stance 3
does not exist. `xmove` is strafe, `ymove` forward, both -127..127; the
physics divides by 127 and clamps the length to 1.

**Weapon parameters** (9 bytes, field order differs from a struct's):

```
u8   flags          bit 0 full automatic, bit 1 slow reload (one round at a
                    time), bit 2 penetrative, bits 3-4 weapon type
u16  fireInterval   ms between shots
u16  reloadTime     ms
u16  raiseTime      ms before it can fire after being taken out
u8   maxDamage      percent of 100 hp
u8   magazineSize   rounds
```

```c
typedef struct {
    uint8_t full_auto, slow_reload, penetrative, type;
    uint16_t fire_interval_ms, reload_ms, raise_ms;
    uint8_t max_damage, magazine;
} p10_weapon_params;

/* the 0.75 rifle as our server sends it */
static const p10_weapon_params P10_RIFLE = {
    0, 0, 0, 0 /* BULLET */, 500, 2500, 500, 49, 10
};
```

`weaponSkin[i]` names the weapon: `rifle`, `smg`, `shotgun`, `rocket`,
`revolver`, empty for none; the gear is `grenade` or `drill`. `bodySkin` is
`class/<name>` in a classes match, else `default`. A skin is lowercase ASCII,
digits and `_ / -`, at most 32 bytes.

**A Player's Create fills all three weapon slots**: the primary, the second
gun (zeros and magazine 0 when the class has none), and the gear. The
`Tool` field then names the slot in hand, so another player's gun is read from
its body — no command announces it.

### 6.5 Trajectory

```
u8    type | 0x80 if a parent entity follows
vec3  origin
vec3  velocity
if type == PLAYER:  vec3 euler        (pitch, roll, yaw; roll is always 0)
else:               rotation          (compact quaternion)
                    vec3 angularVelocity
if parent:          varint parentEntityId
```

| Value | Type | Motion |
| --- | --- | --- |
| 0 | Constant | stays at `origin` |
| 1 | Linear | `origin + velocity·t` |
| 2 | Gravity | `origin + velocity·t + ½·g·t²`, `velocity + g·t`, `g = (0,0,32)` |
| 3 | Player | the player physics, driven by the last input |
| 4 | RigidBody | free body (vehicles; not used by our game) |
| 5 | PlayerCompact | the player trajectory in 17 bytes (below) |

The client extrapolates between updates; positions are **not** samples.

**PlayerCompact** (revision 1.2, what the server sends for every body):

| field | type | value |
| --- | --- | --- |
| type | `u8` | 5, bit 7 = has parent |
| origin x, y | `u16` | position × 64 (1/64 block) |
| origin z | `i16` | position × 64, rounded **up** (toward the sky) |
| velocity x,y,z | `i16` | velocity × 1024 |
| pitch | `i16` | `euler.x × 32767 / (π/2)` |
| yaw | `i16` | `euler.z × 32767 / π` |
| parent | `varint` | if bit 7 |

The decoder hands a compact trajectory on as an ordinary Player one. A client
sends its own trajectory in floats; the server validates it.

### 6.6 `EntityUpdate` (30, S→C)

```
u8      forced        1 = apply even to entities this client owns
item*                  entity update items to the end of the packet
```

The server builds one per tick with every entity whose delta is non-empty.
An update is a **delta**: keep the last value of each part and change only
what the mask announces. An item with `mask == 0` is never sent. An item for
an unknown id without Create is ignored.

A client ignores parts for entities it owns, **unless** `forced` is set or the
item has Create: that is how the server corrects a client it disagrees with.

### 6.7 `ClientSideEntityUpdate` (35, C→S)

```
item*   entity update items to the end (never with Create)
```

You report your own body: trajectory, input when it changed, tool, block
colour. Movement is client-authoritative, but the server checks it:

* Items for entities you do not own are dropped.
* A change of trajectory type is refused and corrected.
* The new position must be within **0.1 block** of the server's extrapolation
  along the old velocity, and the velocity within 0.1; otherwise the server
  sends a `forced` correction.

Send at a steady rate (we use 30 Hz), unreliable on channel 1, with the input
whenever it changed. Send one reliably on channel 0 right before a hit or a
block edit.

### 6.8 `EntityEvent` (31, S→C)

```
varint  entityId
u8      eventType    Jump, ReloadWeapon, Suicide, Explode, Fire, UsePerk
varint  param        event-specific, 0 if unused
```

`ReloadWeapon` on a player tells every client but the reloader to play the
reload sound and refill their view of that player's clip (without it you stop
drawing that player's shots once your count hits 0). `Explode` means a
grenade/rocket/explosive went off. `Jump` lets a body jump at once.

### 6.9 `EntityDie` (32, S→C)

```
varint  entityId
u8      deathType
varint  param
optional damage info (present only when bytes remain after param):
  u8      damageType | 0x80 if fromEntity follows
  vec3    firePosition
  vec3    hitPosition
  varint  fromEntity        (only with 0x80)
```

**Check for the end of the packet before reading the damage type** — a death
without damage info has no such byte.

For a player death, `param = reason | respawnSeconds << 8`, where `reason` is
the 0.75 kill type: 0 weapon, 1 headshot, 2 melee, 3 grenade, 4 fall, 5 team
change, 6 weapon change, 7 sentry, 8 explosive. `fromEntity` is the killer
(omitted for a suicide). This one packet drives the kill feed: victim =
`entityId`, killer = `fromEntity`, weapon/headshot from `damageType`.

### 6.10 `PlayerUpdate` (50, S→C) and player items

```
varint  playerId
u8      mask
  bit 0 Create  -> string name
  bit 1 Score   -> varint score
  bit 2 Flags   -> u8 playerFlags   (bit 0 isAdmin)
  bit 3 Team    -> u8 team          (0, 1, 255 spectator)
  bit 4 Stats   -> varint kills, varint deaths
  bit 5 Ping    -> varint milliseconds
  bit 6 Perks   -> u8 points, u8 inventory, u8 nextThreshold  (owner only)
```

The fields are written **in that order**, which is not the bit order: Create,
Score, Flags, Team, Stats, Ping, Perks.

`Perks` is sent to the owner only: the progress of the perk the HUD is
waiting for, a bitmask of the perks held (`1 << id`), and that perk's
threshold (0 = none left).

### 6.11 `PlayerRemove` (51, S→C)

```
varint*  player ids to the end of the packet
```

### 6.12 `PlayerAction` (60, C→S)

```
u8      eventType    Jump, ReloadWeapon, Suicide, UsePerk
varint  param
```

Your request to act on your own body: `Jump` (the zombie leap carries its
charge in `param`), `ReloadWeapon`, `Suicide` (the pause menu's Respawn), or
`UsePerk` (place a sentry, landmine, dynamite). The server answers with an
`EntityEvent` when it accepts.

## 7. World interaction

### 7.1 `TerrainUpdate` (40, S→C)

A list of edits to the end of the packet. Positions are deltas from a cursor
that starts at `(0,0,0)`:

```
for each edit:
    i8 dx             if dx == -128 (0x80): the cursor moves:
                          varint cx, cy, cz   (absolute, unsigned)
                          i8 dx               (re-read)
    i8 dy
    i8 dz
    position = cursor + (dx, dy, dz)
    u8 health         0 = the block is destroyed; otherwise created
    if health != 0:
        u8 red, green, blue     (yes: R, G, B here)
        u8 createType           (0 unspecified, 1 player)
    else:
        u8 destroyType          (0 unspecified, 1 damage, 2 collapse)
```

**The cursor does not follow the edits**: deltas are always relative to the
last explicit cursor. The encoder emits an absolute cursor when a delta does
not fit in -127..127, then a zero delta.

Example: create an orange block (255,128,0) at (10,20,30), health 100, by a
player:

```
28  0A 14 1E  64  FF 80 00  01
```

Destroy the block at (300,5,63); x does not fit, so the cursor moves:

```
28  80 AC 02 05 3F  00 00 00  00  01
```

A create with health below 100 is a **cracked block** (block health, section
8.3). Cells marked `Collapse` are falling structures: remove them and build
the falling piece from their colours and connections (0.75 clients compute
this themselves; 1.0 clients are told).

Apply a whole packet, then run block physics once. That is the batching 0.75
has to do by hand.

### 7.2 `HitEntity` (90, C→S)

```
varint  entityId      who was hit
u8      hitType       TORSO, HEAD, LIMB
u8      damageType    WEAPON1, WEAPON2, MELEE, ...
vec3    firePosition  where the shot started (your eye)
vec3    hitPosition   the point it met on the body
```

You report hits; the server decides damage. Our server refuses a gun hit
whose `firePosition` is more than 4 blocks from the shooter's eye, whose
`hitPosition` is more than 3 blocks (plus lag tolerance) from the target as
the shooter saw it, or whose line from `firePosition` to just short of
`hitPosition` crosses a solid block.

Send `damageType` as the **slot you fired from** (`WEAPON1` or `WEAPON2`);
the server refuses it if that is not the gun in hand. A melee hit is
`MELEE`.

### 7.3 `HitTerrain` (91, C→S)

```
blockcoord  block        zigzag x, y, z
u8          damageType   DIG, MELEE, WEAPON1..3
vec3        firePosition
vec3        hitPosition
```

The spade's primary is `MELEE` (destroy one block), its secondary is `DIG`
(the block and the ones above and below, i.e. 0.75's 1 x 1 x 3). A gun's hit
is `WEAPON1`..`WEAPON3`; the slot is **not** checked for a block, all three
mean "a bullet".

Our server keeps **block health**: a gun sends a `HitTerrain` for every
pellet that meets a block, and the server subtracts the weapon's damage
(rifle 50, SMG 34, shotgun 20 a pellet, revolver 34) from the cell's 100. At
100 the block breaks; below it the cell goes out in the tick's
`TerrainUpdate` as a solid cell with health `100 - damage` — draw the crack.
A crack heals 10 s after its last hit. The spade still counts on the client
and sends only the hit that breaks the block.

`firePosition` must be within 4 blocks of your eye. A refused hit is answered
with a `TerrainUpdate` carrying the cell's real state, so your prediction is
undone.

### 7.4 `Damage` (92, S→C)

```
varint  entityId                  who took it
u8      damageType | 0x80 if fromEntity follows
varint  fromEntity                (only with 0x80)
varint  toEntity
vec3    firePosition
vec3    hitPosition
u8      amount                    hp removed
```

Use it for the hit indicator (direction from `firePosition`), screen effects
and the local hp. The authoritative hp is the body's `Health` field in
`EntityUpdate`.

### 7.5 `BuildBlock` (93, C→S) and `BuildLine` (94, C→S)

```
blockcoord  block        (BuildBlock)
color       color        B, G, R
---
blockcoord  from
blockcoord  to
color       color        B, G, R
```

Example, block (256,255,62) with r=0x11, g=0x22, b=0x33:

```
5D  80 04 FE 03 7C  33 22 11
```

The server answers with a `TerrainUpdate` using `createType = Player` and the
colour it accepted. Its rules apply: the block tool must be in hand, no
sprinting, a solid neighbour, the block count, the cell must be editable. A
refused build is answered with a `TerrainUpdate` restoring the cell.

**Colour order trap:** `BuildBlock`/`BuildLine` send B, G, R; `TerrainUpdate`
sends R, G, B.

### 7.6 `ThrowGrenade` (95, C→S)

```
vec3  origin      where it leaves the hand
vec3  velocity    blocks per second
f32   fuse        seconds until it explodes (0..3)
```

The decoder rejects NaN/Inf and a negative fuse. A thrown grenade becomes an
entity with a Gravity trajectory, and an `EntityEvent Explode` when the fuse
runs out. None of these go to the thrower: your client shows your own
grenade from the moment you throw it (and keeps it until `Explode`; the fuse
is not on the wire).

### 7.7 `ChatMessage` (70, C→S) and `ChatBroadcast` (71, S→C)

```
u8      channel      0 all, 1 team
string  text         UTF-8, at most 255 bytes
---
varint  fromPlayer   0xFFFFFFFF = the server
u8      channel      0 all, 1 team, 2 system
string  text         UTF-8, at most 255 bytes
```

A client cannot send channel 2 (that would forge server notices). Text is
UTF-8 everywhere: there is no CP437 in 1.0. Our server replays a
`ChatMessage` into the 0.75 chat handler, so mute, spam and `/command` rules
are shared.

Hex, `gg` to the team: `46 01 02 67 67`.
Player 3 says `hi` to all: `47 03 00 02 68 69`.
Server says `Round over`: `47 FF FF FF FF 0F 02 0A 52 6F 75 6E 64 20 6F 76 65 72`.

### 7.8 `GameModeState` (80, S→C)

```
map  state
```

A string map like `GameStateHeader`. **Snapshots and deltas:** a packet whose
first entry is `mode` is a snapshot (forget all mode state, then apply); any
other packet is a delta (each key replaces its value, an empty value removes
the key). The server sends a snapshot right after `GameStateFinal` and at
every round start, and a delta whenever something changes.

Numbers are decimal, lists comma-separated with no spaces, positions are
**block cells** (map coordinates, whole numbers).

| Key | Value | Meaning |
| --- | --- | --- |
| `mode` | `ctf`, `ngctf`, `tc`, `arena`, `zombie`, `koth`, ... | the mode; starts a snapshot |
| `team1-name`, `team2-name` | text | |
| `team1-color`, `team2-color` | `r,g,b` | 0..255 |
| `team1-score`, `team2-score` | decimal | captures, rounds or territories, by mode |
| `capture-limit` | decimal | what wins |
| `team1-intel`, `team2-intel` | `base`, `dropped`, `carried` | state of the intel **belonging** to that team |
| `territory-count` | decimal `N` | TC |
| `territory<i>` | `holder,capturing,permille,rate` | holder 0/1/2, share 0..1000, change a second |
| `arena-state` | `waiting`, `countdown`, `fight`, `end` | Arena |
| `arena-round`, `arena-time`, `arena-winner` | | Arena |
| `zombie-team`, `zombie-humans` | | Zombie |
| `koth-radius`, `koth-state`, `koth-round`, `koth-holder`, `koth-on`, `koth-points`, `koth-winner` | | KotH |

Extrapolate a territory's progress as `permille + rate × elapsed`, clamped to
0..1000, like 0.75's `ProgressBar`.

**Objectives are entities**, and the mode's state only adds what they cannot
say:

* each intel is a `FLAG` entity, each tent a `COMMAND_POST`;
* KotH's hill and TC's territories are `CHECKPOINT`s;
* fixed ids: `0x7FFF0000` + 0 = team 1's intel, 1 = team 2's, 2 = team 1's
  tent, 3 = team 2's, 4 = the hill, 5 + i = territory i;
* a carried intel has its trajectory's `parentEntityId` set to the carrier
  and its origin meaningless;
* the intel's state word (`base`/`dropped`/`carried`) tells the rest.

The server sends an objective's `EntityUpdate` **before** the
`GameModeState` that goes with it, in the same tick.

Babel is sent as `ctf`. A client that does not know a mode shows the scores.

## 8. Our additions to the reference

None of this exists in ngspades; all of it is implemented in our server and
client. A minimal client can ignore most of it and still play.

### 8.1 `GenericCommand` (9, both)

```
bytes*  parts to the end of the packet: parts[0] is the command
```

Unknown commands are logged and ignored on both sides. Rare, human-readable
actions live here; frequent or structured data gets its own packet id.

Commands a client must or may send:

| Command | Meaning |
| --- | --- |
| `join <team> <weapon> [<class>]` | create your player: team 0/1 (255 spectator), weapon 0 rifle, 1 SMG, 2 shotgun; class 0..3 in a classes mode |

| `map-cached <0\|1>` | your answer to the map header (section 5.1) |
| `team <n>` | change team in game (0, 1, 255) |
| `weapon <n>` | change weapon in game |
| `class <n>` | pick a class (classes modes); refused in others |

### 8.2 Perks: jetpack and sentry

Rules (server-side, summarized): a perk is earned with per-life progress and
granted by the server; nothing is pressed to get one.

Wire:

* `GameStateFinal` world parameters: `jetpack-*` (only when the server has
  one), `sentry-lifetime`.
* Entity flag bit 3 `jetpack` on the owner's body while it is equipped.
* Input bit 4 `jetpack` while you want thrust (in the creative mode the same
  bit is "held jump = fly up").
* `PlayerUpdate` `Perks` bits, to the owner only.
* `PlayerAction UsePerk` with
  `param = id | x << 8 | y << 20 | z << 32` places a sentry/landmine/
  dynamite on the floor cell `(x,y,z)`.
* `GenericCommand perk-activated`, `perk-refused`, `perk-next`.

The owner integrates fuel with the same step as the server; fuel is not on
the wire.

### 8.3 Classes

A mode with classes (`ngctf`, and the zombie mode when the host allows them)
gives every player one of four classes. The class decides the gun (the body's
first weapon slot), the health (`hp` stays 0..100 on the wire and every
damage is scaled by `100 / classHealth`), the speed, the sprint, the jump,
the block wallet, the fall damage and the melee. A second gun is
`WEAPON2`; the gear (grenades, or the Miner's drill) is `WEAPON3`.

A client reads everything else from the `class-info <n> <key> <value>`
commands the server sends after `classes 1` and on every change. The class is
picked with `class <n>` or the fourth part of `join`.

`wallet <n>` is the server's block count for you (protocol 1.0 has no block
count anywhere else): follow it after every build and dig.

### 8.4 The match summary

At the end of a match the server sends one `match-player` per player in a
team and then `match-end`, and reloads the map 16 s later. A client may show
a summary or ignore both.

## 9. Minimum for a working client

Implement in this order; each step is independently testable against a real
server.

1. **Transport**: ENet with 2 channels and the 1.0 connect data (or WebRTC).
   Log packet ids; ignore unknown ids.
2. **Primitives**: the varint codec with the strict decoder rules (§3).
   Encode a `Greeting` reply? No — receive it, then send `InitiateConnection`.
3. **Handshake**: `InitiateConnection` with `"WorldOfSpades 1.0"` and
   `mapQuality = 0`, so you only need the VXL loader. Certificates with
   `isValid = 0`. You are in the game when `GameStateFinal` arrives.
4. **Map**: `GameStateHeader` → `MapData` × N → `MapDataFinal` → decode →
   apply the `TerrainUpdate`s kept during the transfer →
   `MapDataAcknowledge`. Send `map-cached 0` if you do not cache yet.
5. **World**: `GameStateFinal`, `EntityUpdate`, `PlayerUpdate`,
   `PlayerRemove`, `EntityRemove` with the delta rule, the player trajectory
   and its compact form, and the jetpack bits (decode and ignore).
6. **Join and move**: `join <team> <weapon>`, read `local-player`, then send
   `ClientSideEntityUpdate` at 30 Hz and watch your body move on the server.
7. **Combat**: `HitEntity`, `HitTerrain`, `Damage`, `EntityDie`.
8. **Building and chat**: `BuildBlock`, `BuildLine`, `ThrowGrenade`,
   `ChatMessage`, `ChatBroadcast`, `TerrainUpdate`.
9. **Game mode**: `GameModeState` for CTF, plus the `FLAG`/`COMMAND_POST`
   entities.
10. Then the rest: ngmap, classes, perks, the summary.

### 9.1 A first-session test script

```
connect                         -> Greeting arrives
send InitiateConnection         -> ServerCertificate
send ClientCertificate (0)      -> GameStateHeader
(download)                      -> MapDataFinal
send MapDataAcknowledge         -> GameStateFinal
send "join 0 0"                 -> local-player 0, EntityUpdate with Create
send ClientSideEntityUpdate     -> the server accepts (no forced correction)
fire at a wall                  -> HitTerrain, TerrainUpdate from the server
```

If the server drops you at any point, its log says which check failed. The
wire only gives a number.

## 10. Pitfalls

1. **Masks are not self-describing.** One unknown bit means the packet cannot
   be decoded; reject it (and know that adding a bit is a protocol change).
2. **Field order ≠ bit order** in entity items and player items.
3. **`TerrainUpdate` is R,G,B; every other colour is B,G,R.**
4. **Compact trajectory z rounds up** (toward the sky). Rounding to nearest
   puts a standing body inside the floor and the client's step-up makes every
   body bob.
5. **Ignore `EntityUpdate` parts for your own entity** unless `forced` or
   Create, or you fight your own prediction.
6. **Send the update before the action.** A hit or a build without a
   preceding input report is refused (`not_firing`, wrong tool).
7. **Check the end before reading `EntityDie`'s damage info.**
8. **Unknown packet ids and map keys are ignored; unknown mask bits are
   errors.**
9. **The server may restart the transfer at any time** (`GameStateHeader`);
   drop the world, take the new map, `join` again.
10. **A `MapDataAcknowledge` is mandatory** after decoding.
11. **`map-format` decides the decoder**, not `mapQuality`.
12. **A WebRTC message over 16 KB is refused**; game packets never need to be
    that large, but your own extensions must respect it.
13. **Text is UTF-8**; there is no CP437 in 1.0. If you bridge to 0.75 data,
    convert at the boundary.

## 11. The server side (if you run one)

Our server is a SpadesX fork. A 1.0 server must:

* accept the connect magic (or WebRTC `connect`), send `Greeting`, and run
  the handshake with its timeouts;
* send the map (`vxl` or `ngmap`) and hold the `TerrainUpdate`s for loading
  connections;
* implement `GameStateFinal`, `EntityUpdate` as deltas per receiver,
  `PlayerUpdate`, `EntityRemove`, `PlayerRemove`, `TerrainUpdate` (batched per
  tick), `EntityEvent`, `EntityDie`, `Damage`;
* validate hits (line of sight, distance, fire rate), builds (tool, reach,
  block count, editable cells) and movement (the 0.1-block window);
* implement `GameModeState` for at least CTF.

Log every refused packet with a reason (`EVT <player> <event> why=...`); it
is the only way to debug an implementer's first session.
