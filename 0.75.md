# Ace of Spades 0.75 and 0.76

The classic protocol, spoken by the original Voxlap client, OpenSpades,
BetterSpades, our client and every public Ace of Spades server. If your game
wants to join a public server today, this is the protocol it has to speak.

**0.76 is 0.75 with three differences** (marked `[0.76]` throughout): another
connect data value, a larger `MapStart`, and a `WorldUpdate` that carries a
player id per entry. Everything else is identical, so one implementation can
speak both.

Companion documents: [`1.0.md`](1.0.md) (our protocol), [`master.md`](master.md)
(server list, addressing, how a client joins from a browser).

---

## 1. Transport

| Setting | Value |
| --- | --- |
| Transport | ENet 1.3 over UDP (IPv4; IPv6 is not part of 0.75 but our server accepts it) |
| Port | 32887 by convention |
| Channels | 1 (channel 0) |
| Compression | ENet's range coder (`enet_host_compress_with_range_coder`) |
| Connect data | `3` = 0.75, `4` = 0.76 |
| Reliability | everything reliable **except** `WorldUpdate` (2), which the server sends unreliable |
| Framing | one ENet packet = `u8 packet id` + payload |

```c
ENetHost *host = enet_host_create(NULL, 1, 1, 0, 0);
enet_host_compress_with_range_coder(host);      /* mandatory: decompression too */
ENetPeer *peer = enet_host_connect(host, &address, 1, 3); /* 3 = 0.75, 4 = 0.76 */
```

The range coder is negotiated: if the server compresses and you do not
decompress, every packet after the handshake is garbage. Turning it on for
both directions is always correct.

### 1.1 Disconnect reasons

The server passes a `uint32` with the disconnect event. ENet also uses 0 for
a timeout, so 0 is ambiguous.

| Value | Meaning |
| --- | --- |
| 0 | timed out, or an unspecified server reason |
| 1 | banned |
| 2 | kicked (some servers: too many connections from your address) |
| 3 | wrong protocol version |
| 4 | server full |
| 5 | server shutting down |
| 8, 9, 10, 11 | banned, full, kicked, wrong version — sent after the map download instead of during it |
| 20 | invalid name |
| 61 | server shutting down (an alternative value some servers use) |

Show anything else as "unknown"; never index a table with the number.

A **system chat message from player 255 sent just before the disconnect is
the kick text.** Servers use that to explain a kick (the "Kick Reason"
extension, section 9).

### 1.2 Addresses (`aos://`)

```
aos://<address>[:<port>][<version suffix>]
```

* `<address>` is the IPv4 address as one decimal number in **little-endian**
  byte order: `aos://16777343` is `127.0.0.1` (`0x0100007F`). Byte 0 of the
  address is the low byte of the number.
* `<port>` defaults to **32887**.
* A suffix after the port (`:0.75`, `/0.76`) names a version. An unknown
  suffix means 0.75.

```c
uint32_t n = strtoul(text, NULL, 10);
snprintf(ip, sizeof ip, "%u.%u.%u.%u",
         n & 255, (n >> 8) & 255, (n >> 16) & 255, (n >> 24) & 255);
```

Accept a dotted address and a bare `host:port` too; every modern client does.

## 2. Data representation

* Every integer is **little-endian**; signed ones are two's complement.
* `float` is IEEE-754 binary32.
* Structures are **packed**: no padding.
* A colour is 3 bytes in **B, G, R** order.
* `vec3i` is three `int32`.

```c
#pragma pack(push, 1)
typedef struct { float  x, y, z; } vec3f;
typedef struct { int32_t x, y, z; } vec3i;
typedef struct { uint8_t b, g, r; } color3;
#pragma pack(pop)
```

### 2.1 Coordinates

The map is **512 x 512 x 64** voxels.

* `x` goes east (0..511), `y` goes south (0..511), `z` goes **down**: 0 is the
  sky, 63 is the bottom layer.
* A float position `(0,0,0)` is the corner of voxel `(0,0,0)`;
  `(0.5,0.5,0.5)` is its centre. Floor each axis to get the voxel.
* A player's position is its **eye**, not its feet. A standing player's feet
  are about 1.5 blocks lower (`z + 1.5` in map coordinates).
* The bottom two layers, `z = 62` and `z = 63`, cannot be dug.
* Terrain outside 0..511 on `x`/`y` is drawn as a copy of the map
  (toroidal wrap). Players, block edits and block physics do **not** wrap;
  grenades do.
* Looking direction is the vector `(ox, oy, oz)`, unit length, `oz` negative
  when looking up (because `z` grows downwards).

If your engine has `y` up (OpenGL, Godot, Unity), convert at the protocol
boundary: `internal = (x, 63 - z, y)` for positions and
`(x, -oz, oy)` for directions, and back on send.

### 2.2 Sectors

The minimap grid is 8 x 8 sectors of 64 x 64 columns. Sector letter
`A`..`H` = `floor(x / 64)`, digit `1`..`8` = `floor(y / 64) + 1`.
Territory captures are announced by sector index.

### 2.3 Text

Two encodings are in use:

* **CP437**, the original one. Bytes `0x80`..`0xFF` are the IBM PC code page.
* **UTF-8**, sent by newer servers. A string that starts with byte `0xFF` and
  is valid UTF-8 after it is UTF-8 (drop the `0xFF`); anything else is CP437.
  To send, use CP437 when every character fits, otherwise `0xFF` + UTF-8 —
  and only to a server known to read it (section 9.1).

A name is a NUL-terminated string. The classic limit is 15 characters; a
name that does not fit is refused or replaced by the server.

Chat text may contain colour control bytes:

| Byte | Colour |
| --- | --- |
| `0x01` | team 1's colour |
| `0x02` | team 2's colour |
| `0x03` | spectators' colour |
| `0x04` | red |
| `0x05` | green |
| `0x06` | normal (white) |
| `0x07` | grey |
| `0x08` | yellow |

`\n` and `\r` break the line. Other bytes below `0x20` are shown as a
replacement character.

## 3. A connection, step by step

```
client                                        server
  ENet connect (data 3) ---------------------->
              <------------------------  MapStart (18)        compressed size
              <------------------------  MapChunk (19) x N
              <------------------------  VersionGet (33)      optional
              <------------------------  HandshakeInit (31)   optional
  VersionSend (34) --------------------------->               optional
  HandshakeReturn (32) ----------------------->               optional
              <------------------------  ExistingPlayer (9)   for each player in
              <------------------------  StateData (15)       download done
  ExistingPlayer (9) ------------------------->               team/weapon choice
              <------------------------  CreatePlayer (12)    you spawn
              <------------------------  WorldUpdate (2), ...  the match
```

1. **Connect** with data `3`. The server checks the version, bans and free
   slots, then sends the map.
2. **Map**: `MapStart` gives the total compressed size; append every
   `MapChunk` payload in arrival order. The concatenation is a **zlib stream
   of a VXL map** (512 x 512 x 64). Do not start decoding before the byte
   count matches; a lost chunk is a corrupted map.
3. **State**: `StateData` ends the download. Decompress and load the map,
   take your player id, the fog colour, the team names and colours, the game
   mode and its scores/objectives from it.
4. **Join**: show the team and weapon menus and send `ExistingPlayer` with
   your id, team, weapon, tool (gun), block colour and name. Choosing the
   spectator team joins at once. Older clients send `ShortPlayerData` (id,
   team, weapon).
5. **Spawn**: the server answers with a `CreatePlayer` for you (and for
   everyone else whenever anyone spawns). Only then are you alive.

While the map transfers, a server may send `VersionGet` and/or
`HandshakeInit`; answer them (section 7.10) and nothing else changes.

When a new round starts with a new map, the server sends `MapStart` again
and the whole sequence repeats: your client must be able to receive a map
mid-game.

## 5. Server → client packets

### 0 `PositionData` — teleport / correction (S→C)

```c
struct { vec3f pos; };   /* 13 bytes with the id */
```

Puts **your** player at `pos` at once. Used for a teleport (`/tpc`), for a
spawn correction, and to undo a client whose position the server refused.
It carries no player id: it is always about the receiver.

Client: set your position, zero your velocity, keep the look. Never
interpolate — it is a correction, not a movement.

### 1 `OrientationData` — turn (S→C)

```c
struct { vec3f ori; };   /* 13 bytes */
```

Turns **you** to the unit vector `ori`. Rare; normally `WorldUpdate` carries
looks.

### 2 `WorldUpdate` — the world (S→C, **unreliable**)

```c
/* 0.75: 24 bytes per slot, indexed by player id */
struct { vec3f pos; vec3f ori; };           /* 1 + 24 n */
/* 0.76: 25 bytes per slot, id in front, only present players */
struct { uint8_t player_id; vec3f pos; vec3f ori; };  /* 1 + 25 n */
```

Up to 256 slots (0.75) or up to the server's player limit (0.76). It is the
only packet sent unreliable: a newer update replaces the old one.

* Skip your own slot. Your own movement is local.
* **A slot whose position is `(0,0,0)` means "not visible": keep the last
  known position.** Servers use zeros for dead players, players out of the
  fog and free slots.
* Interpolate between updates (about 60 a second) for smooth movement.
* The orientation is a unit vector; do not assume it is normalised if you
  are writing a server — normalize it before sending.

### 3 `InputData` — movement keys of another player

```c
struct { uint8_t player_id, keys; };   /* 3 bytes */
```

Key bits: `1` forward, `2` back, `4` left, `8` right, `16` jump, `32` crouch,
`64` sneak, `128` sprint.

For **yourself** only the jump bit matters (the server echoes the physics it
applied). Others use it to animate legs and stance.

### 4 `WeaponInput` — fire buttons of another player

```c
struct { uint8_t player_id; uint8_t primary : 1, secondary : 1; };  /* 3 bytes */
```

`primary` is the left button (fire/build/dig), `secondary` the right
(aim/dig). It is not the raw mouse: a server sends 0 while a player
sprints, switches tool or reloads. The client uses it to draw tracers,
swings and muzzle flashes for that player. Ignore it for yourself.

### 5 `SetHP` — your health (S→C)

```c
struct { uint8_t hp, type; vec3f source; };   /* 15 bytes */
```

`hp` is your new health 0..100. `type` is `0` fall damage and `1` anything
else. `source` is where the damage came from (zero for a fall); the client
points its damage indicator there.

A drop in health flashes the screen red; a hit sound plays (for gun damage).
Do not treat it as authoritative beyond 0: when `hp` reaches 0 the
`KillAction` follows.

> Packet id 5 is `SetHP` from the server and `Hit` from the client. Direction
> decides which it is.

### 6 `Grenade` — a grenade in flight (S→C)

```c
struct { uint8_t player_id; float fuse_length;
         vec3f pos, vel; };   /* 30 bytes */
```

Spawns a grenade that explodes `fuse_length` seconds after the packet
arrives, at `pos`, moving with `vel`.

**`vel` is in blocks per 1/32 s**, not blocks per second: divide by 32 for a
physics engine that works per second. Gravity is 32 blocks/s² downwards.
The server does not echo a grenade to its thrower (the client already shows
its own).

### 7 `SetTool` — tool in hand

```c
struct { uint8_t player_id, tool; };   /* 3 bytes */
```

Tools: `0` spade, `1` block, `2` gun, `3` grenade. Ignore a value above 3.

### 8 `SetColor` — block colour

```c
struct { uint8_t player_id; color3 color; };   /* 5 bytes */
```

The colour that player's blocks are built with. Keep it even for a player
who is not alive or not joined yet: later `BlockAction` packets use it.

### 9 `ExistingPlayer` — a player already in the match (S→C)

```c
struct { uint8_t id; int8_t team; uint8_t weapon; uint8_t tool;
         uint32_t kills; color3 color; char name[]; };  /* 11 + name */
```

Sent for every other player after the map and before `StateData`.

* `team`: `0` team 1, `1` team 2, `-1` (255 on the wire) spectator.
* `weapon`: `0` rifle, `1` SMG, `2` shotgun.
* `tool`: as in `SetTool`.
* **It carries no position.** Keep the player hidden until a `WorldUpdate`
  or a `CreatePlayer` places them.
* The name is NUL-terminated CP437; read to the end of the packet if the NUL
  is missing (some servers omit it).

### 11 `MoveObject` — an objective moved

```c
struct { uint8_t object; int8_t team; vec3f pos; };   /* 15 bytes */
```

CTF: object `0`/`1` are team 1's/team 2's intel, `2`/`3` their tents.
`pos` is the new cell; moving an intel also drops it from its carrier
silently. TC: `object` is a territory index and `team` its new owner
(`0`, `1`, `2` = neutral).

### 12 `CreatePlayer` — a player spawned (S→C)

```c
struct { uint8_t id, weapon; int8_t team; vec3f pos; char name[]; };
/* 15 + name; a 16-byte packet has an empty name */
```

That player spawns at `pos` (its **eye**), or joins the first time. The
player is alive unless `team` is spectator. It faces east for team 1 and
west for team 2. Reset its block colour to `(111,111,111)` and restock it
(full hp, 50 blocks, 3 grenades, full magazine and reserve).

Two compatibility notes:

* The original Voxlap client draws the player at `pos.z - 2` (two blocks
  higher, i.e. the feet). Modern clients use `pos` as given. If you build
  both, follow the client you are.
* A packet exactly 16 bytes long carries no name: keep the one you had.

### 13 `BlockAction` — a block changed (S→C)

```c
struct { uint8_t player_id, action_type; vec3i pos; };   /* 15 bytes */
```

| Type | Effect |
| --- | --- |
| 0 | build one block with the player's colour (a repaint when the cell is already solid, silently) |
| 1 | destroy one block |
| 2 | spade: destroy the block and the ones above and below it (1 x 1 x 3) |
| 3 | grenade: destroy 3 x 3 x 3, silently |
| 4 | destroy one block (a gun) |
| 5 | destroy one block (a spade) |

Types 2 and 3 leave the bottom layers (`z >= 62`) alone. Cells outside the
map are ignored. For yourself a build costs one block and a spade destroy
gives one back (up to 50) if you count blocks locally.

**Apply edits that arrive together together.** Collect every `BlockAction`
and `BlockLine` of the frame into a table keyed by position (create or
destroy, the last one wins), then apply the creates, then the destroys, then
run block physics once. Servers rely on this to repaint a block (a destroy
followed by a build at the same cell): applying them one by one makes a
structure resting on that cell collapse in between.

### 14 `BlockLine` — a line of blocks was built

```c
struct { uint8_t player_id; vec3i start, end; };   /* 26 bytes */
```

Builds a line of blocks between the two cells (a 3D DDA), skipping cells
that are already solid. It costs `|dx| + |dy| + |dz| + 1` blocks.

### 15 `StateData` — the match (S→C), ends the download

```c
struct {
    uint8_t player_id;              /* you */
    color3  fog, team1_color, team2_color;
    char    team1_name[10], team2_name[10];  /* NUL padded, may lack the NUL */
    uint8_t mode;                   /* 0 CTF, 1 TC */
    union {
        struct {                    /* 52 bytes */
            uint8_t team1_score, team2_score, capture_limit;
            uint8_t intel_bits;     /* bit 0: team 1's intel held, bit 1: team 2's */
            /* 12 bytes per intel: held = { u8 carrier; u8 pad[11]; }
                                  else  = { vec3f pos; } */
            uint8_t intel1[12], intel2[12];
            vec3f   team1_base, team2_base;
        } ctf;
        struct {                    /* 1 + 13 n */
            uint8_t count;
            struct { vec3f pos; uint8_t team; } territories[16];
        } tc;
    } data;
};
```

Sizes: 83 bytes for CTF (`31 + 52`), `32 + 13n` for TC.

* Read the team names as 10 bytes that may not be NUL-terminated.
* Treat an unknown mode as TC.
* `player_id` is you. Load the map only now, then open the team menu.
* `team*_base` are the tents; `intel*` is held by the player in byte 0 or
  lying at `pos`.
* TC: `team` is `0`, `1` or `2` (neutral).

### 16 `KillAction` — someone died (S→C)

```c
struct { uint8_t victim, killer, kind, respawn_seconds; };   /* 5 bytes */
```

`kind`: `0` weapon, `1` headshot, `2` melee, `3` grenade, `4` fall,
`5` team change, `6` class change. A suicide has `victim == killer`. The
killer scores unless it was a suicide. Draw the kill feed and start the
respawn countdown from `respawn_seconds`.

### 17 `ChatMessage` — chat or a notice

```c
struct { uint8_t player_id, type; char text[]; };   /* 3 + text, NUL included */
```

Types: `0` all, `1` team, `2` system. Newer servers also send `3` big,
`4` info, `5` warning, `6` error — show those as popups, only if you agreed
to the Message Types extension.

A system message (`type` 2) from player 255 sent just before a disconnect is
the kick reason: show it as the disconnect text.

Text is CP437 or `0xFF` + UTF-8 (section 2.3); strip the `0xFF` and decode.

### 18 `MapStart` / 19 `MapChunk` — the map

```c
/* 0.75 */
struct { uint32_t map_size; };                      /* 5 bytes */
/* 0.76 */
struct { uint32_t map_size, crc32; char name[64]; } /* 73 bytes */
struct { uint8_t data[]; };                         /* 1 + n */
```

`map_size` is the length of the whole **zlib-compressed VXL**. Append chunk
payloads (any size, in order) until you have `map_size` bytes, then inflate
and load. A 0.76 server: before it sends the map, answer `MapCached` (31)
with 1 if your cache holds the map with that CRC32 (then it sends no
chunks), 0 otherwise.

The 512 x 512 x 64 VXL format is a column-major voxel format; use `libvxl`
or port its reader. It is the same bytes our 1.0 protocol sends when
`map-format` is `vxl`.

### 20 `PlayerLeft`

```c
struct { uint8_t player_id; };  /* 2 bytes */
```

Clear the slot: the player is gone.

### 21 `TerritoryCapture` / 22 `ProgressBar` — TC

```c
struct { uint8_t index, winning, team; };            /* 4 bytes */
struct { uint8_t index; int8_t team, rate; float progress; };  /* 8 bytes */
```

`winning` ends the round. `team` is `0`, `1` or `2` (neutral). The bar's
`progress` is 0..1; `rate` is progress per 50 s (the client advances
`0.05 * rate` a second).

> Some clients read an uninitialized pointer when `team` is not 0/1; your
> server should only send 0, 1 or 2.

### 23 `IntelCapture` / 24 `IntelPickup` / 25 `IntelDrop` — CTF

```c
struct { uint8_t player_id, winning; };              /* 3 bytes */
struct { uint8_t player_id; };                       /* 2 bytes */
struct { uint8_t player_id; vec3f pos; };            /* 14 bytes */
```

A capture is 10 points to the player and 1 to the team; `winning` ends the
round. A drop gives the cell the intel now lies at.

### 26 `Restock`

```c
struct { uint8_t player_id; };  /* 2 bytes */
```

That player gets full health, 50 blocks, 3 grenades and a full reserve. For
yourself update the HUD; for someone else only play the sound. Ignore it
while you are dead.

### 27 `FogColor`

```c
struct { uint8_t alpha; color3 color; };  /* 5 bytes */
```

The new fog colour. 0.75 has no fog distance: it is always 128 blocks.

### 28 `WeaponReload`

```c
struct { uint8_t player_id, ammo, reserved; };  /* 4 bytes */
```

The magazine and reserve after an accepted reload. For yourself set the
ammo; for another player only play the reload sound (and refill your view of
their clip, or you stop drawing their shots).

### 31 `HandshakeInit` / 33 `VersionGet` — optional fingerprinting

```c
struct { int32_t challenge; };   /* 5 bytes */
/* VersionGet: 1 byte; the extended form adds a list of property ids */
```

Answer `HandshakeInit` with `HandshakeReturn` (32) carrying the same 4 bytes,
and `VersionGet` with `VersionSend` (34). Neither is required; a server must
never require them (the Voxlap client answers neither).

## 6. Client → server packets

A server validates all of these. What a client has to send is below; what a
server does with them is in section 11.

### 0 `PositionData`

```c
struct { vec3f pos; };   /* 13 bytes */
```

Your eye position. Send about once a second while alive, and immediately
after a teleport or a correction. The server compares it with its own
simulation and answers with `PositionData` when it disagrees.

### 1 `OrientationData`

```c
struct { vec3f ori; };   /* 13 bytes */
```

Your look, unit vector. Send when it changed by more than ~0.5 degrees, up
to ~120 times a second, and **right before every shot** so the server can
validate the hit's direction.

### 3 `InputData`

```c
struct { uint8_t player_id, keys; };   /* 3 bytes */
```

Your movement keys, whenever they change. `player_id` is you.

### 4 `WeaponInput`

```c
struct { uint8_t player_id; uint8_t primary : 1, secondary : 1; };
```

Whenever a fire button changes, except while sprinting (sprinting drops the
trigger). `player_id` is you.

### 5 `Hit`

```c
struct { uint8_t victim, hit_type; };   /* 3 bytes */
```

For every hit your shot or swing made: `hit_type` `0` torso, `1` head,
`2` arms, `3` legs, `4` melee. The server decides damage. Send only hits you
really saw; servers check distance, line of sight and fire rate, and a lying
client is a cheat.

### 6 `Grenade`

```c
struct { uint8_t player_id; float fuse;
         vec3f pos, vel; };   /* 30 bytes */
```

You throw: `fuse` seconds left (up to 3), where it leaves the hand, and
velocity **in blocks per 1/32 s** (`blocks_per_second / 32`). `player_id`
is you.

### 7 `SetTool` / 8 `SetColor`

```c
struct { uint8_t player_id, tool; };
struct { uint8_t player_id; color3 color; };
```

Whenever your tool or block colour changes. `player_id` is you.

### 9 `ExistingPlayer` — joining

```c
struct { uint8_t id; int8_t team; uint8_t weapon; uint8_t tool;
         uint32_t kills; color3 color; char name[]; };
```

Send after `StateData`, with your id, the chosen team (`-1` = spectator),
weapon, tool (gun), `kills` 0, your block colour and your name. The server
answers with a `CreatePlayer`.

**The extended version answer** (section 9.1) reuses this id: the first byte
after the id is `'x'` (0x78), which no 0.75 player id can be.

### 10 `ShortPlayerData`

```c
struct { uint8_t id, team, weapon; };   /* 4 bytes */
```

The older join form. Servers accept it too.

### 13 `BlockAction`

```c
struct { uint8_t player_id, action_type; vec3i pos; };
```

Types: `0` build (needs the block tool and at least one block), `1` destroy
one (spade or gun), `2` spade dig (1 x 1 x 3). `player_id` is you. The
server checks the tool, the distance (about 4 blocks), sprinting, the map
bounds, the bottom layers, building being enabled, and the block count.

### 14 `BlockLine`

```c
struct { uint8_t player_id; vec3i start, end; };
```

A dragged line of blocks. It costs one block per cell on the line.

### 17 `ChatMessage`

```c
struct { uint8_t player_id, type; char text[]; };
```

`type` is 0 all, 1 team. The server relays it with your id. The text is
NUL-terminated and the NUL is part of the packet. A line starting with
`0xFF` is UTF-8 (only send it to a server known to read it).

### 28 `WeaponReload`

```c
struct { uint8_t player_id, ammo, reserved; };
```

You start a reload: send your current magazine and reserve. The server
answers with `WeaponReload` (28) when it finishes. Some servers reload the
gun themselves and a client that adds ammo locally disagrees after a tool
switch or a shot; the safe pattern for a 0.75 server is: play the animation,
count the shells, and let the server's answer settle the ammo.

### 29 `ChangeTeam` / 30 `ChangeWeapon`

```c
struct { uint8_t player_id, team; };
struct { uint8_t player_id, weapon; };
```

From the in-game menus. Changing team or weapon during a match is a death
(kind 5 or 6) followed by a respawn.

### 31 `MapCached` `[0.76]`

```c
struct { uint8_t cached; };   /* 2 bytes */
```

Answer the 0.76 `MapStart`: 1 = you have the map with that CRC32, send no
chunks; 0 = send it.

### 32 `HandshakeReturn` / 34 `VersionSend`

```c
struct { int32_t challenge; };
struct { uint8_t client; uint8_t major, minor, revision;
         char operatingsystem[64]; };
```

`client` is a letter: `'B'` for BetterSpades and our client, `'o'` for
OpenSpades. Answer `HandshakeInit` with the same 4 bytes.

### 114 Flashlight Light (optional)

```c
struct { uint8_t sub; uint8_t player; uint8_t on; };  /* sub 0 */
```

Ask to switch your light. Send it only after the server offered the
Flashlight extension (0x32) and you accepted it; wait for the server's relay
before drawing the beam.

## 7. Game rules the client must implement

The protocol carries state; the game still needs rules. These are the ones
the wire assumes.

### 7.1 Players

Ids 0..255; most servers use 32 slots but keep state for all 256. Per
player: joined, alive, team, weapon, tool, score, name, block colour,
position, orientation, input. Only for yourself: hp, blocks, grenades,
magazine, reserve.

Out-of-range values fall back to something safe (spectator, rifle, spade);
never index a table with a value from the wire.

### 7.2 Fog

Sight is a cylinder of radius 128 around the camera: nothing beyond is
drawn, shots stop there, the sky is the fog colour. `StateData` and
`FogColor` set the colour. A server may send positions of players beyond the
fog anyway; do not draw them (that is a wallhack).

### 7.3 Block physics

When a voxel stops being solid, check its six neighbours. Each solid one
starts a flood fill through solid voxels. If the fill reaches the ground
layer (`z >= 62`), nothing happens; otherwise everything it reached is
detached, falls and is removed.

Voxels that were **already empty** inside a spade or grenade area must not
start a check (they are not newly detached).

### 7.4 Damage, death and respawn

You report hits; the server sends `SetHP`, then `KillAction` at 0. On death
you drop the intel if you carry it (the server sends `IntelDrop`), your
corpse is drawn (or a grave), the kill feed updates and the respawn counter
runs from `KillAction.respawn_seconds`. The server spawns you with a
`CreatePlayer`.

### 7.5 Blocks

A player carries at most 50 blocks. A build costs one, a spade destroy (of
your own blocks) gives one back. `Restock` refills you at your tent. The
client counts locally for the HUD; the server counts for the rules.

### 7.6 CTF state from `StateData`

Two scores, a capture limit, two intels (held by a player or lying at a
cell), two tents. Touching the enemy intel picks it up (`IntelPickup`),
carrying it into your tent captures it (`IntelCapture`), dying drops it
(`IntelDrop`). A capture puts the intel back at its base (`MoveObject`). A
round ends at the capture limit.

### 7.7 TC state from `StateData`

A list of territories (position + owner). Standing in one moves its capture
towards your team; the server sends `ProgressBar` and then
`TerritoryCapture`. Owning them all wins.

## 8. Extensions (optional)

Servers may offer extensions; each is used only by the clients that agreed.
The registry and the full packet layouts are the **aosprotocol
specification** (https://github.com/zerospades/aosprotocol).

### 8.1 The handshake

```
server: ExtInfo (60)   u8 count, then count x (u8 id, u8 version)
client: ExtInfo (60)   the subset both sides know: u8 count, then (id, version) pairs
```

A client **must answer with the intersection**, never with an extension the
server did not offer, and never with one it does not implement. After that,
an extension's packets may arrive; a client that did not agree must ignore
them.

Extension ids (the packet of an extension is `0x40 + id` unless noted):

| Id | Name | Packet | What it does |
| --- | --- | --- | --- |
| `0x00` | Player Properties | 64 | exact health, blocks, grenades, ammo and score of players |
| `0x20` | Damage Markers | 96 | hit markers and damage numbers |
| `0x30` | Teamplay | 112 | config, pings, ESP marks, teammate names |
| `0x31` | Pie Menu | 113 | server-defined quick-chat rings |
| `0x32` | Flashlight | 114 | per-player lights |
| `0x33` | Daytime & Weather | 115 | time of day and weather |
| `0x35` | Player Outfit | 117 | how players look (a draft) |
| `0xC0` | Player Limit | — | how many players the server accepts |
| `0xC1` | Message Types | — | chat types 3..6 |
| `0xC2` | Kick Reason | — | the kick text as a system line |

### 8.2 Player Properties (0x00, packet 64)

```
u8  packet id 64
u8  sub = 0
u8  player_id
u8  health      (0 for an enemy: only you and your team see it)
u8  blocks
u8  grenades
u8  clip
u8  reserve
u32 score
```

Sent when a value changes, at most every 100 ms per player. Our server sends
it; a client that agrees should use it for the HUD's exact ammo and the
scoreboard.

### 8.3 Flashlight (0x32, packet 114)

Sub `0` is the client's request (`Light`), sub `1` the relay of a player's
light, sub `2` the light config, sub `3` the light state. The server relays
a request to everyone that agreed, using the sender's id. A light goes off
silently on `CreatePlayer`, `KillAction`, `PlayerLeft` and a new map; the
server sends nothing for those, so every client does the same. Do not
invent a light the server did not relay.

### 8.4 UTF-8 chat (no id)

A chat line or name starting with byte `0xFF` is UTF-8 (section 2.3). A
client should tell the server it reads it through the extended version
answer's feature bit 0, and only then send `0xFF` lines itself.

### 8.5 Extra Packets (version handshake)

After a plain `VersionSend` the server may ask for more:
`HandshakeInit` (31), then an extended `VersionGet` (33) whose payload is a
list of property ids. Answer with `ExistingPlayer` (9) whose first byte is
`'x'`, then per property `id, length, payload`, one packet per property,
each repeating the ones before:

| Id | Meaning | Payload |
| --- | --- | --- |
| 0 | application | e.g. `BetterSpades 0.1.5` |
| 1 | language | e.g. `en_us`, `pt_br` |
| 2 | feature flags | bit 0: reads UTF-8 chat |

An unknown id gets an empty payload.

## 9. The server list and joining

The classic public list is a JSON array at `/serverlist.json`, for example
`https://services.buildandshoot.com/serverlist.json`. Each entry has at
least:

| Key | Example | Notes |
| --- | --- | --- |
| `name` | `"Deuces Wild"` | |
| `identifier` | `"aos://16777343:32887"` | the address to join |
| `map` | `"Hallway"` | |
| `game_mode` | `"ctf"` | |
| `country` | `"US"` | ISO 3166-1 alpha-2 |
| `latency` | `120` | ms, measured by the list |
| `players_current`, `players_max` | `16`, `32` | |
| `last_updated` | `1301931731` | Unix seconds |
| `game_version` | `"0.75"` | |

Ignore keys you do not know and expect duplicates.

Our master serves the same JSON shape (plus `id`, `identifier6`, `info`) at
`https://master.shootanddestroy.obex.pw/v1/servers`; a row with
`"game_version": "0.75"` is one of our servers running the 0.75 profile.
Fetching, merging and filtering lists, IPv4/IPv6 choice, LAN discovery and
the UDP `HELLOINFO` details are in [`master.md`](master.md).

### 9.1 Connecting

Desktop: ENet, as in section 1. A browser cannot send UDP: a browser
**cannot join a 0.75 server** unless somebody relays it. Our WebRTC
transport is protocol 1.0 only ([`1.0.md`](1.0.md) section 3.4,
[`master.md`](master.md) section 5).

A resilient client tries the protocols in order: 1.0 magic, then `3`, then
`4`. A vanilla server refuses the 1.0 magic at once with reason 3, so the
fallback costs one round trip. Some servers accept any connect data and
then speak 0.75; treat "any game packet before the protocol's first expected
packet" as a failed attempt and reconnect.

## 10. Writing a 0.75 server

If you are on the other side, the minimum set that makes 0.75 clients work:

**Must**

1. An ENet host with the range coder, accepting connect data 3 (and 4).
2. Version, ban, capacity checks with the right disconnect reasons.
3. Map: VXL, zlib, `MapStart`, `MapChunk`.
4. `ExistingPlayer` for every player, then `StateData`, after the map.
5. The join (`ExistingPlayer`/`ShortPlayerData`), then `CreatePlayer` to
   everyone.
6. `WorldUpdate` at a steady rate, unreliable, zeros for unseen slots.
7. Relay and validate `InputData`, `WeaponInput`, `SetTool`, `SetColor`,
   `OrientationData`, `PositionData`.
8. `Hit` → `SetHP` → `KillAction` → respawn.
9. `BlockAction` and `BlockLine` with validation, block physics, `Restock`.
10. Chat and `PlayerLeft`.
11. At least CTF.

**Should**

* Server-side movement physics with corrections.
* `CreatePlayer` for players that do not move (bots) when someone joins,
  or they stand at the map corner until the next `WorldUpdate`.
* Grenades simulated on the server.
* `VersionGet`/`HandshakeInit`, as optional checks.
* `0xFF` + UTF-8 for text CP437 cannot express, to clients that read it.
* `ExtInfo` and the extensions.

Spawn a player with 100 hp, 50 blocks, 3 grenades, a full magazine and
reserve, the gun in hand and no input held. When hp reaches 0, send
`KillAction` and spawn again after the delay. Send every packet reliable
except `WorldUpdate`, and one game packet per ENet packet.

## 11. Checklist and pitfalls

1. **Do not forget the range coder.** Without it, nothing after the first
   bytes decodes.
2. **`z` is down and a position is the eye.** Nearly every "players float"
   bug is this.
3. **`WorldUpdate` zeros are "not visible", not the origin.**
4. **`ExistingPlayer` has no position.** Hide the player until one places it.
5. **Batch block edits per frame**, creates then destroys, then physics.
6. **Grenade velocity is per 1/32 s.**
7. **Check every packet length**, and the `player_id` on client packets.
8. **A slot id from the wire is not an array index** until you validated it.
9. **The extended version answer reuses packet 9** and starts with `'x'`.
10. **Only send an extension packet to a client that agreed to it.**
11. **A server may send the map again mid-game**; handle `MapStart` at any
    time.
12. **Chat may be CP437 or UTF-8 with a `0xFF` prefix**; both can arrive in
    one session.

Once a connection works, log the first 64 bytes of every packet in hex for
one session and compare the sequence with section 3. It is the fastest way
to see which side is out of step.
